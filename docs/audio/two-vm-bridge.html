The two-VM audio bridge

How tesserae's browser build plays undertone today: the game's lg VM in a worker sends commands, and a second lg VM on the page plays them. Spike of 2026-10-14, branch spike/undertone-audio.

The problem

lg -w runs the game in a Web Worker so it can block on keys without freezing the page. A worker has no AudioContext, so the game can't open WebAudio itself. Something on the main thread has to own the audio device.

The shape

Web Worker

lg VM #1: the gamestock lg -w bundle, no undertone linked
↓
tesserae.sfxbackend :bridge (no audio/trigger, but *in-wasm*)
↓

→let-go host relays as a window CustomEvent

Main thread

undertone-bridge.jsbuffers early events, loads the bridge wasm, replays
↓
lg VM #2: the bridgeGo wasm with audio natives, embedded ambience, and undertone.bridge/handle!
↓
undertone engine → webaudioAudioContext + worklet, started on first gesture
↓
🔊 speakers

Only control-rate data crosses the gap: a parameter set every few seconds and the odd one-shot. PCM is produced entirely on the page.

One command, end to end

  1. A tile breaks. The game calls (sfx/tile-broken! combo wx), which debounces and builds {:shot :tink :degree 4 :gain 0.5 :pan 0.3}.
  2. sfx sees backend :bridge and calls (js/emit "undertone" {:form "[:trigger {...}]"}).
  3. let-go's wasm host receives the worker message and dispatches a CustomEvent("undertone") on window.
  4. The bridge's Go listener checks detail.form is a string and pushes it onto a 256-deep channel. The handler never blocks the wasm scheduler; a burst past 256 drops.
  5. A goroutine drains the channel: c.Def the string, then runs (undertone.bridge/handle! (read-string ...)) in VM #2.
  6. handle! dispatches on the op and calls audio/trigger. The engine voices it into the ring the worklet reads.

Wire format

CommandBridge doesSent by sfx when
[:score mood seed level tension]ambience/derive-mood, then audio/set-parametersa level loads, tension changes
[:params {...}]audio/set-parameters(available, unused)
[:trigger m]audio/triggertile broken or cracked, wall struck, etc.
[:music-gain g]audio/set-music-gainstart!

Sending :score rather than a derived parameter map is why the bridge carries ambience: the mood derivation runs on the page, so the worker's VM never needs undertone at all.

Details that made it work

  • Early commands. The bridge wasm is larger than the game and finishes loading after the game's first :music-gain and :score. The loader listens from page load, holds those events, and re-dispatches them once window.undertoneBridge exists.
  • Gesture unlock. The bridge calls m.Start() at load, which blocks until the first gesture anywhere on the page. Creating the context inside a later handler misses that gesture. Triggers before then drop; score and gain updates stick.
  • Write-only. Nothing flows back to the worker, so autoplay and replays stay deterministic. undertoneBridge.stats() exposes {received, errors, started} for tests only.
  • Same game code everywhere. sfx.lg picks :native when the lg links undertone (tools/play-audio.sh), :bridge in wasm, and nil otherwise, where every call is a no-op.
  • Build. tools/build-web-audio.sh runs the stock build-web.sh with a shell that has the loader script injected, builds cmd/undertone-bridge for js/wasm, and copies Go's wasm_exec.js beside it.

Trade-offs

Why it's attractive

  • No changes to let-go: js/emit and the worker host are stock.
  • The game bundle stays the stock one.
  • Tiny, text-only protocol that's easy to log and test.
  • Audio rendering never competes with the game's thread.

What it costs

  • Two wasm runtimes and two lg VMs on one page. As of 2026-10-14 the bridge wasm was about 29 MB beside an about 9 MB game page.
  • A second Go runtime and wasm_exec.js to load and keep in step.
  • The early-event buffering dance.
  • EDN print and read on every command.

Where it went next

The follow-up spike (2026-10-15) collapses it to one VM: the game wasm links undertone itself (let-go -import from #1037, with ambience registered through #1064's RegisterEmbeddedSource). Undertone renders in the worker into a SharedArrayBuffer ring and posts it to the page, where a small page.js owns the AudioContext and worklet. That drops the second runtime and the EDN hop, at the cost of rendering on the game's thread. The fallback, if that cost shows up, is a plain-Go bridge with no lg VM on the page.
